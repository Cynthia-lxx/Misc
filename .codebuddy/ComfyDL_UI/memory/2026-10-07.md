## 2. Crash site spike——执行现场快照/恢复可行性实证（全部通过，未立项）

用户设想（git-fire 精神映射）：叫停/报错时分析在野数据 → 用户选择性保存（单
SQLite 库 或 多文件+manifest）→ 杀死执行 → 反向恢复续跑；衍生玩法 = 恢复时篡改
数据流看效果。四层可救性分析：A 已完成节点输出（可救）、B 执行中节点内部状态
（= 训练 checkpoint 基建，另立项）、C prompt/queue（易救）、D 进程（语义待定）。

**Spike 实验**（临时脚本 `​.tmp_spike_crashsite.py`，进程内真实 PromptExecutor +
3 节点链 + mock server，harness._bootstrap 沙箱，**10/10 通过后已删**）：

1. **报错后 cache 存活 ✅**：node3 抛错 → handle_execution_error 后 break（execution.py
   :800/:824），caches.outputs 里已完成节点的 CacheEntry(ui, outputs) 原样可取。
   **抢救窗口 = 报错后到下次 set_prompt**；同 prompt 重 Queue 时 set_prompt 同 keys
   + clean_unused 保留条目（窗口对恢复场景不关闭）。
2. **恢复 = 同 prompt 重 Queue，宿主自动跳过 ✅**：修复后重跑，node1/2 cache hit
   零重执行、仅 node3 跑——**"恢复注入 cache 后从断点续跑"不需要任何新机制**，
   宿主缓存天生支持。
3. **⚠ 核心机制发现：宿主缓存判定是 hash 驱动而非存在性驱动**——is_changed key
   由 prompt 输入结构递归计算；**手动注入 CacheEntry（甚至把下游条目 set(None)）
   都不会触发下游重算**（第一次两次尝试失败的原因）。推断：node3 hash 未变时
   根本不会向上游递归。
4. **tamper 正解 = prompt 改写 + 常量注入节点 ✅**：把目标节点的上游链接换成
   常量节点（execute 返回新值，类型匹配）→ 下游 hash 变化 → 从注入点重算，且
   未触及的上游零重跑——全程走宿主正道（validate/hash/cache 全兼容），实现时
   需按输出类型备几个 typed 常量节点。
5. **窗口关闭实证 ✅**：Queue 不同 prompt → 旧 prompt 条目被 clean_unused 清掉。

**格式映射注意**：IMAGE 是 float32，png 有损——抢救默认应存 safetensors，png
留给导出视图。DB 形态：每快照一个独立 SQLite（BLOB + manifest 表），std sqlite3
直开，不进 user db。

**结论**：crash site 技术可行性全部成立，无阻断项；tamper 语义按"prompt 改写 +
常量注入"设计。下一步 = 用户确认 scope 后进 bigplan（M1 自动全量单库 capture +
同机恢复；M2 汇总表/多文件/跨机；M3 训练 checkpoint 并入）。

## 4. M1 验收堵点修复：index.html 启发式缓存吞掉新面板（2026-10-08，父仓 `db52d00`，**103 commits**）

**现象**：用户重启整机多次仍看不到 Crash Site tab（profiling tab 正常）。
**排查链**：index.html 内 tag 存在（单行大文件 read_file 截断曾误判"无 tag"——
大文件必须 findstr 验证）；curl 实测 /comfydl/crashsite/crashsite.js 200、
/snapshots 200、/ 返回的 index.html 含 tag；官方 sidebar 文档核对注册契约一致；
用户 Console 无任何 crashsite 报错也无请求痕迹 → 唯一自洽解释 = **浏览器缓存的
旧 index.html**。
**根因**：`middleware/cache_middleware.py` 对 .js/.css/index.json 加 no-store，
但对 `/`（index.html，无扩展名）**不设任何缓存头** → 浏览器启发式缓存长期沿用
旧版 → 新增的 loader tag 永远到不了浏览器。"整机重启"不清 HTTP 缓存。
**修复**：cache_middleware 对 `/`、`/index.html`、`*.html` 设 `Cache-Control:
no-cache`（可缓存但必须 revalidate）——此后前端补丁变更即时生效，无需硬刷新。
**顺带修复**：profiler.js 的 server log 卡一直 404——`/internal` 是 subapp 挂在
/api 孪生循环之外，fetchApi 自动补的 /api 前缀必然 404；改为原生 fetch 直连
`/internal/logs/raw`（M3 以来的潜伏 bug，用户从未见到 server log 卡有内容）。
**教训入档**：①单行大文件（index.html）的内容断言必须 findstr，read_file 会
截断；②诊断"前端没出现"类问题第一件事查缓存中间件与 index.html 缓存头；
③Console 无报错 + 无请求痕迹 = 脚本根本没被加载（而非加载失败）。

## 6. 双层修复后仍炸 → 宿主 registerExtension 是 pinia store 包装（父仓 `736ac5a`，**106 commits**）

双层 getApp 修后用户日志给出决定性堆栈：`registerExtension → useExtensionService
→ useStore → Cannot read properties of undefined (reading '_s')`——**新版宿主
（frontend 1.51.9）的 app.registerExtension 是 Vue pinia store 包装**，在 Vue
services 初始化完成前调用必抛 `_s` undefined；而 crashsite.js 的手写 wait 循环
无 try/catch——**一次异常炸死整个重试循环**（只重试了一次就死）。profiler 存活
是因为它的 `waitFor` 轮询自带 try/catch（L555-561）。
**修复 = 全盘照抄 profiler 骨架**（用户指令"抄现成的"）：
①`waitFor(fn, limit, step)`（catch 在轮询内）等待 app 就绪；
②registerExtension 调用包 try/catch + 无限重试直至成功（services 热身窗口）；
③**setup 钩子不可依赖**——注册成功时机可能晚于宿主的 setup 遍历（竞态），故
registerExtension 成功后**手动调 init()**，setup 钩子作为冗余路径，init 用
`state.initialized` 防重入；
④按用户指令新增**顶栏按钮**（ComfyButton/ComfyButtonGroup 注入
`app.menu.settingsGroup.element.before`——与 Run/Jobs 并列，profiler badge 同款
范式），双入口：侧栏 tab + 顶栏按钮。
**教训**：宿主扩展 API 的调用时序契约（pinia 就绪窗口）比 API 形状本身更隐蔽——
凡是包装 store 的宿主 API，调用点必须 try/catch + 重试，且不能依赖宿主的回调
遍历必然覆盖自己（晚注册者须手动拉起）。
